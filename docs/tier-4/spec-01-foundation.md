# SPEC-01. Основа: вход, роли, журнал, идемпотентность

## Задача

Каркас сервера и клиента, на котором строятся остальные функции: вход владельца и администратора, проверка прав на сервере, журнал действий, защита от повторной отправки, единое правило округления.

## Состав

1. Схема БД: `branches`, `users`, `sessions`, `operations`, `audit_log`, `settings`, счётчики номеров документов.
2. Первичная настройка: если пользователей нет, при старте создаются филиал «Основной» и владелец из `BOOTSTRAP_OWNER_LOGIN` / `BOOTSTRAP_OWNER_PASSWORD`. Без этих переменных и без пользователей сервер пишет предупреждение и работает (вход невозможен).
3. Эндпоинты:
   - `POST /auth/login {login, password}` → cookie + `{user}`.
   - `POST /auth/logout`.
   - `GET /auth/me` → `{id, login, full_name, role, branch_id}`.
   - `GET /users`, `POST /users`, `PATCH /users/{id}` — только владелец. Нельзя деактивировать или понизить последнего активного владельца.
4. Модуль денег `domain::money`: единственная функция деления с округлением.

## Алгоритм

**Вход**
```
найти активного пользователя по login (без учёта регистра)
если нет или argon2.verify(password) ложь → 401 (одинаковый ответ, задержка не раскрывает наличие логина)
token = 32 случайных байта; хранить sha256(token)
expires_at = now + 30 дней
cookie avtodom_session = hex(token)
журнал: auth.login
```

**Ограничение перебора** (ADR-016)
```
ключ = логин в нижнем регистре
если login_attempts[ключ].locked_until > now → 429 «повторите через N мин»
неудача → failures += 1 (сброс до 1, если прошлой неудаче больше 15 мин)
failures ≥ 5 → locked_until = now + 15 мин, failures = 0
успех → удалить запись
```
Неизвестные логины учитываются так же, как существующие.

**Проверка сессии** — извлекатель `CurrentUser` в каждом защищённом обработчике: cookie → sha256 → сессия не истекла → пользователь активен. Иначе 401. `RequireOwner` — дополнительно `role = owner`, иначе 403.

**Устройство** — извлекатель `DeviceId`: заголовок `X-Device-Id`, UUID. Для изменяющих запросов обязателен, иначе 422.

**Идемпотентность**
```
fn run_operation(op_id, kind, user, f):
  tx = begin
  если в operations есть op_id:
     если kind или user другие → 409
     вернуть сохранённый response
  resp = f(tx)
  insert operations(op_id, user, kind, resp)   -- при гонке unique violation → rollback, прочитать сохранённый ответ
  commit
  вернуть resp
```

**Журнал** — `audit(tx, ctx, action, entity, entity_id, data)` в той же транзакции. Таблица `audit_log` защищена триггером от изменения и удаления (ADR-014).

**Округление**
```
div_round(n, d): целочисленное деление с округлением половины от нуля; d > 0
  q = n / d, r = n % d
  если 2·|r| ≥ d → q += sign(n)
```
Расчёт в i128, результат проверяется на вхождение в i64.

## Клиент

- Экран входа, хранение `device_id` в localStorage (создаётся один раз).
- Каркас приложения: меню по ролям, выход.
- Экран «Пользователи» для владельца.
- Общая функция запросов: добавляет `X-Device-Id`, при 401 ведёт на вход.
- Форматирование: `formatSom(tyiyn)` → «1 234,50 с», `formatLiters(ml)` → «2,5 л». Только для показа.

## Дополнено SPEC-29, часть B (19.10.2026)

Права сверх роли (ADR-082): владелец выдаёт администратору отдельное право в карточке пользователя — `PATCH /users/{id} {permissions}` (список целиком, только владелец, неизвестное право — 422), хранится в `user_permissions`. Пока одно право — `oil_transfer` («Перелив масла», SPEC-14). `GET /users`, `GET /auth/me` и ответ входа отдают `permissions`; меню показывает пункт по праву, проверяет сервер.

## Дополнено SPEC-30 (21.10.2026)

Права администратора выбирает владелец (ADR-097, расширяет ADR-082). Список — `auth::PERMISSIONS` (ключ, подпись, группа, по умолчанию), на экране — `web/src/lib/permissions.ts`; тест `permissions_match_the_screen_list` сверяет оба списка. Права: `sale_return`, `sale_debt`, `discount` (нет), `debt_payment`, `cash_moves`, `expenses`, `payroll_pay`, `receipts`, `stock_in`, `supplier_returns`, `defects`, `revision`, `oil_transfer` (нет), `battery_intake`, `products`, `clients`.

- Хранятся в `user_permissions`; миграция `0056_admin_permissions` выдала существующим администраторам все права «да» (пустой `granted_by`), выданный раньше `oil_transfer` сохранён. Новый администратор (`POST /users` или смена роли владельца на администратора) получает права по умолчанию.
- `PUT /users/{id}/permissions {op_id, permissions}` — только владелец, список целиком; неизвестное право или пользователь-владелец — 422; повтор `op_id` — тот же ответ. Журнал `user.permissions`: кому, что включено (`granted`) и выключено (`revoked`); пишется, только если что-то поменялось, и попадает в уведомления владельца. `PATCH /users/{id}` права больше не меняет (заменяет способ из SPEC-29, часть B).
- Сервер проверяет право у каждого действия администратора (`auth::require_permission`, владелец проходит всегда): без права — 403 «Нет права: <подпись>». Чек в долг без сети без права проводится с причиной владельцу (`sale.offline_bypass`).
- Право закрывает: `sale_return` — возврат по чеку; `sale_debt` — оплату `debt` в чеке; `debt_payment` — оплату долга клиента; `cash_moves` — внесение, изъятие, перевод и их сторно; `expenses` — расходы и их сторно; `payroll_pay` — выплаты (и при закрытии смены); `receipts` — приход, его сторно, фото накладной, оплату поставщику, накладные по фото; `stock_in` — оприходование; `supplier_returns` — возврат поставщику; `defects` — отметку брака и её снятие; `revision` — ревизию (кроме проведения); `oil_transfer` — перелив; `battery_intake` — приём аккумуляторов; `products` — категории, карточки, штрихкоды, кросс-номера, минимальный остаток; `clients` — клиентов, людей фирмы, машины и записи книжки.
- Правом не выдаются: себестоимость, прибыль, маржа, «Исправить», цены, отмена перелива, начисления, бонусы, удержания, проведение ревизии, сторно выплат и приёма аккумуляторов, правка долга.
- Без проверки права администратору остаются: открытие, закрытие и сдача смены, мастера, услуги без цен, поставщики, этикетки, просьба о лимите, отклонённые чеки без сети.
- Экран: «Настройки» → «Пользователи» → «Что можно» — флажки по группам; колонка «N из 16». Пункты меню и кнопки без права скрыты.

## Критерии приёмки

- [ ] Неверный пароль и несуществующий логин дают одинаковый ответ 401.
- [ ] Администратор получает 403 на `/users`.
- [ ] Повтор запроса с тем же `op_id` возвращает тот же ответ и не создаёт вторую запись.
- [ ] `UPDATE`/`DELETE` в `audit_log` отклоняются базой.
- [ ] `div_round`: 5/2=3, −5/2=−3, 7/3=2, 1/3=0, 2/3=1.
- [ ] Нельзя отключить последнего владельца.
- [ ] После 5 неудачных попыток вход по логину с этого адреса блокируется на 15 минут (429), в том числе с верным паролем; другие логины и другие адреса не затронуты. Попытки во время блокировки её не продлевают (ADR-049, ADR-059).
- [x] Неверные пароли к одному логину с многих адресов вход не закрывают: 20 за 15 минут — уведомление владельцу «Подбирают пароль» (`auth.login_flood`), владелец со своего адреса входит (ADR-059).

## Дополнено SPEC-33 (24.10.2026)

- Филиал запроса: администратор — всегда свой филиал; владелец — филиал из заголовка `X-Branch-Id` (выбор в шапке, помнит устройство), без заголовка — свой; неизвестный филиал — 422. В закрытом филиале изменения — 409.
- `/auth/me` и ответ входа: `branch_id` (филиал запроса), `home_branch_id`, `branch_name`, `branches` (владельцу — все, администратору — свой), `several_branches`.
- «Пользователи»: владельцы видны из любого филиала, администраторы — своего филиала; «последний владелец» считается по всем филиалам.
