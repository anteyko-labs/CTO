# SPEC-15. Ревизия склада

## Задача

Раз в месяц (BLUEPRINT §6, вопрос 22) на точке пересчитывают товар сканером по категориям. Система показывает, сколько должно быть, принимает пересчитанное и выравнивает остатки движениями с причиной. Для масла действует норма расхождения (вопрос 32, ADR-052): по умолчанию 0,5 % от того, что должно быть, владелец меняет её на экране «Ревизия» (от 0 до 10 %). Строка масла с расхождением больше нормы помечается «сверх нормы», в пределах — «в норме»; уведомление о проведении ревизии называет число таких строк. Остатки выравниваются по пересчитанному в любом случае.

## Данные

```
revisions (id, branch_id, number, category_id?, status draft | posted | cancelled, comment,
           user_id, device_id, created_at, posted_by?, posted_at?)
revision_lines (revision_id, product_id, counted_qty, user_id, updated_at)       -- черновик, правится
revision_results (revision_id, product_id, expected_qty, counted_qty,
                  qty_delta, value_delta_tyiyn)                                   -- неизменяемая
```

Пока ревизия — черновик, пересчитанное можно править: это ещё не учёт. Проведённая ревизия не меняется (инвариант 4), исправление — новой ревизией.

## Проведение

`POST /revisions/{id}/post {op_id, comment}` — только владелец, причина обязательна.

```
в run_operation:
  ревизия — черновик, иначе 409
  lock остатков пересчитанных товаров в порядке id
  для каждой строки: expected = текущий остаток (на момент проведения, а не открытия:
      продажи во время пересчёта учтены), delta = counted − expected
  delta < 0: стоимость уходит по средней (cost_of), как у продажи
  delta > 0: стоимость = delta × средняя за единицу, а при нулевом остатке — по последней закупке
  apply_movement(doc_type = revision), revision_results
  audit revision.post {number, строк, недостача и излишек в деньгах}; владелец видит в уведомлениях
```

Непересчитанные товары категории не трогаются: «не нашли» — это пересчитанный 0. Расхождение в деньгах входит в себестоимость дня, как переоценка (ADR-044): недостача уменьшает прибыль, излишек увеличивает.

## API

- `POST /revisions {category_id?, comment?}` — новый черновик (владелец и администратор).
- `GET /revisions` — список. `GET /revisions/{id}` — товары категории с ожидаемым остатком, пересчитанным и разницей; администратору без стоимости (инвариант 13).
- `PUT /revisions/{id}/lines {product_id, counted_qty, mode?}` — записать пересчёт (штуки или мл) → `{counted_qty}` итог строки. `mode`: `set` (по умолчанию) — записать как есть, остаток «на момент пересчёта» берётся сейчас; `add` — прибавить к уже посчитанному (товар в нескольких местах), атомарно, остаток остаётся от первого пересчёта (ADR-059). `GET /revisions/{id}/lines/{product_id}` → `{counted_qty}` (null — ещё не считали). `DELETE /revisions/{id}/lines/{product_id}` — убрать (в журнал `revision.line_delete` с посчитанным). `PUT` принимает необязательный `op_id`: повтор того же ввода (обрыв связи) возвращает прежний ответ и не прибавляет `add` дважды (ADR-062).
- `POST /revisions/{id}/post`, `POST /revisions/{id}/cancel`.

## Клиент

Экран «Ревизия» в разделе «Склад»: список ревизий и кнопка «Начать». В черновике — поле сканера: каждый скан штучного товара прибавляет 1, у масла фокус встаёт на поле литров. Таблица: товар, должно быть, пересчитано, разница (цветом). Владелец проводит ревизию кнопкой «Провести» с причиной.

SPEC-29 §10: экран «Ревизия и товары» — вкладки «Ревизия» и «Сканер товаров» (SPEC-20). В черновик вписывают и товар, которого нет в программе: «+ Товар не из программы» или скан незнакомого кода — карточка (подсказки из старой программы) заводится сразу с найденным количеством одной операцией `POST /revisions/{id}/new-product`; остаток на момент пересчёта — 0, излишек оценивается по закупке из карточки.

## Критерии приёмки

- [x] Пересчитали меньше — движение «ревизия» на недостачу по средней себестоимости, остаток равен пересчитанному.
- [x] Пересчитали больше — излишек по средней, при нулевом остатке — по последней закупке.
- [x] Продажа во время пересчёта учтена: разница считается от остатка в момент пересчёта строки (`stock_at_count`), продажи и приходы после пересчёта остаются в учёте (ADR-054).
- [x] Карточку объединили или убрали в архив после пересчёта — ревизия не проводится, 409.
- [x] Проведённую ревизию не изменить, повторное проведение — 409; провести может только владелец.
- [x] Расхождение в деньгах — в себестоимости дня отчёта о прибыли.
- [x] Масло: 0,5 л из 100 л при норме 0,5 % — «в норме», 0,501 л — «сверх нормы»; штучный товар нормой не помечается.

## Дополнено задачей 003 (Н14, 31.10.2026)

Один товар лежит в нескольких местах, его считают разные люди с разных устройств — итог складывается, ничья прибавка не теряется.
- Скан в черновике шлёт прибавку: `PUT /revisions/{id}/lines {mode: "add", counted_qty: 1 шт или 1 канистра, op_id}`; на экране — итог строки из ответа сервера.
- Поле строки — с режимом «+ добавить» / «= итог». «+ добавить» — то, что человек нашёл в своём месте, прибавляется к общему итогу (`add`); «= итог» — итог строки целиком (`set`). По умолчанию «+ добавить», если строку уже кто-то считал, иначе «= итог»; масло в таре — всегда «+ добавить» (канистры сканом, вскрытая канистра литрами); весовой товар и масло без тары после скана — «+ добавить». Выбранный режим строки на устройстве держится, пока его не сменят. Итог строки — подписью «итого …» рядом с полем.
- «= итог» сверяется с тем, что человек видел, когда начал ввод, плюс его собственные записи строки, ушедшие после этого и записанные (`lib/revisionCount.ts OwnWrites`), — не с итогом из ответа своей записи: в нём чужие прибавки, которых человек не видел. Видел посчитанное — `expected_qty: N`; видел строку непосчитанной — `expected_empty: true`: «строки нет» и «посчитано 0» («не нашли») — разное, 0 другого человека не затирается молча. Не совпало — 409 `count_changed` «Пока вы вводили, итог строки изменили: сейчас N (строка не посчитана). Записать итог M?»; экран перечитывает строку и переспрашивает: «Записать итог M», «Прибавить M — будет N+M», «Отмена». Очистка поля в «= итог» — `DELETE …/lines/{product_id}?expected_qty=N|expected_empty=true&op_id=…`, с той же проверкой; строки уже нет — не ошибка; пустую строку, которую не трогали, экран не убирает вовсе.
- `DELETE` строки идемпотентен, как `PUT`: повтор с тем же `op_id` (ответ потерялся) возвращает прежний ответ, а не 409 по чужой свежей прибавке.
- «= итог» без `expected_qty` и `expected_empty` шлёт только экран до обновления (вкладка открыта днями; механизма версии клиента в программе нет): строку, которую за последние 10 минут прибавляли с других устройств, — 409 `client_outdated` «Обновите страницу: на кассе старая версия программы…»; иначе запись без проверки, как раньше. То же у очистки строки (`DELETE …/lines/{product_id}` без `expected_*`).
- op_id — правило ввода (`InputOps`): один и тот же не записанный ввод (то же число в поле или форме после неудачи) уходит с тем же `op_id`, пока не придёт успешный ответ или человек не изменит ввод; новый ввод (в том числе каждый скан) — новый `op_id`. При обрыве связи или тайм-ауте экран сам повторяет тот же запрос (до 2 раз); не помогло — число остаётся в поле, повторное нажатие уходит с тем же `op_id`. Сервер не прибавит дважды (ADR-062). Одно правило — в строке ревизии, «Сканере товаров» (пересчёт найденного, новая карточка) и окне «Товар не из программы». «Прибавить M» из окна «пока вы вводили» переводит поле в «+ добавить» с тем же числом и уходит тем же `op_id`, что Enter в этом поле: ответ потеряли — повтор не прибавит второй раз; записано — поле очищается.
- Неотправленные сканы: скан (штука, канистра) встаёт в очередь устройства по ревизии (`lib/revisionQueue.ts`, в памяти и в localStorage — переживает перезагрузку) и уходит на сервер; ответа нет и после автоматических повторов — остаётся в очереди со своим `op_id`, у строки — «⏳ +1 шт не отправлено» (следующий скан её не стирает), вверху — «Не отправлено: N — отправится при связи» и «Отправить сейчас». Очередь уходит сама: раз в 5 с, при возврате сети (`online`) и при следующем ответе сервера — с теми же `op_id`, поэтому дошедший без ответа скан не задваивается, недошедший — не теряется; пересканировать не нужно. Сервер отказал (ревизию провели) — скан уходит из очереди, причина — на экране. В окне проведения при непустой очереди этого устройства — предупреждение «не отправлено сканов: N — без связи они не войдут в ревизию».
- «Товар не из программы»: `op_id` — по введённому (форма вместе с найденным): то же после обрыва — тот же `op_id`; изменили (найдено 5 → 6) — новый, а нажатия без ответа уходят с ним (`prev_op_ids`). Одно из них уже завело карточку — сервер отвечает тем нажатием (`earlier: true`, второй товар не заводится, и без кода тоже); экран записывает исправленный итог («= итог» со сверкой с записанным тогда), строку с тех пор считали другие — открывает строку товара.
- Версия строки: `revision_line_adds.seq` — номер записи по порядку вставки под замком черновика. Ответы `PUT`/`DELETE`/`GET …/lines/{product_id}` несут `version` строки, `GET /revisions/{id}` — `version` у каждой строки и у ревизии (последняя запись). Экран черновика перечитывает ревизию раз в 5 с и при возврате на вкладку; поле, которое сейчас правят, не затирается. Ответ своей записи и перечитывание показываются по строке, только если они новее показанной; строка, которой нет в ответе, остаётся, если показана новее всего ответа (`mergeLines`, `patchIfNewer`) — старый итог не возвращается поверх нового, в каком бы порядке ни пришли ответы. `GET /revisions/{id}` и `GET …/lines/{product_id}` читают итог и версию из одного снимка базы (REPEATABLE READ). Проведённая или отменённая ревизия на экране в черновик не возвращается ответом перечитывания, ушедшего раньше (`freshRevision`).
- Кто сколько посчитал: журнал строки `revision_line_adds` (только пополняется, I5) — каждая прибавка, итог и «убрал», в порядке записи (`seq`, время — `clock_timestamp()`), а не по времени начала транзакции; `GET /revisions/{id}` у строки — `counted_log [{by, mode, qty}]`, прибавки одного человека подряд — одной записью; на экране «считали: Айбек +2 шт, Нурлан +1 шт, Азиз = 5 шт». `counted_by` — кто записал строку последним.
- Скан кода товара этой ревизии (весь склад или её категория), которого нет в загруженном списке (его только что завёл другой или остатка не было): строка появляется сразу, список перечитывается; штука и канистра считаются сразу, на вес и масло без тары — открывается поле. Товар не этой ревизии — «не входит в эту ревизию».
- «Товар не из программы»: тот же код в ту же минуту завёл другой — 409 «штрихкод … уже у товара «…»»; экран находит товар по коду и прибавляет найденное к нему: «Этот товар только что завёл другой — добавили к нему». Найденное пересчитывается в единицы этого товара (`qtyInUnits`): штуки — штуками, канистры — по его таре, масло без тары — литрами; не перевести (литры к штучному, штуки к маслу без тары или к весовому) — не прибавляется молча: открывается строка товара с подсказкой «у него другие единицы — впишите найденное в строке». Найденный товар из другой категории (ревизия категории) — не прибавляется: «Код … уже у товара «…» из другой категории — в эту ревизию он не входит».
- Одна ревизия на всех: любой `POST /revisions {category_id?}` (прежний флаг `reuse_draft` не нужен и не влияет — экран до обновления тоже не заведёт второй черновик) под замком черновика филиала отдаёт открытый черновик того же охвата; охваты пересекаются — ревизия категории при открытом «весь склад» присоединяется к нему, «весь склад» при открытой ревизии категории — 409 `revision_open` «Идёт ревизия «…» — закончите или присоединитесь», на экране — кнопка «Присоединиться»; две ревизии одной категории — одна. Двух черновиков, вычитающих один остаток, не бывает.
- Проведение: товар посчитан и в другом открытом черновике (заведён до этой проверки или товар перенесли в другую категорию) — 409 `revision_overlap` «„…“ посчитан и в открытой ревизии № N — проведите или отмените одну из них». За последние 60 с строки записывали другие люди — 409 `still_counting` «Ещё считают: Нурлан 20 с назад. Провести?»; в окне проведения — предупреждение и «Провести всё равно» (`force: true`, тот же `op_id`). Свои записи владельца не мешают.
- Запись пересчёта в проведённую или отменённую ревизию — 409 `revision_closed` «Ревизия № N уже проведена (Имя); ваш скан не учтён — проведите оприходование или новую ревизию»; экран ревизии перечитывается, «Сканер товаров» следующий пересчёт ведёт в новый черновик.
- [x] Четыре человека одновременно сканируют один товар (`add` по 1) — итог 4; повтор того же `op_id` не прибавляет; одновременное начало — один черновик; «= итог» с устаревшим `expected_qty` — 409, чужие сканы целы; журнал «Айбек +2, Нурлан +1, Владелец = 5» и не правится; две одновременные «Начать» одной категории — один черновик; «весь склад» и категория одновременно — один черновик; «строки нет» и «посчитано 0» различаются в «= итог» и очистке; повтор `DELETE` с тем же `op_id` — прежний ответ, чужой скан цел; охваты не пересекаются и без `reuse_draft`, проведение товара из двух черновиков — 409; старый экран без `expected_qty` при чужих прибавках — 409 `client_outdated`; журнал — в порядке записи; версия строки растёт с каждой записью; «Ещё считают» перед проведением и `revision_closed` после; итог и версия при перечитывании — из одного снимка; очистка строки старым экраном при чужих прибавках — 409 `client_outdated`; «Завести» с исправленным найденным после потерянного ответа — второй карточки нет (`server/tests/concurrent_count.rs`). Два устройства сканируют один товар — у обоих итог; «+ добавить» второго складывается; «= итог» при чужом скане переспрашивает; масло: один сканирует канистры, другой вписывает вскрытую литрами — итог сложился; обрыв связи после записи (автоматический повтор и повторное нажатие) — итог не задвоился; «Прибавить» из окна «пока вы вводили» после обрыва — поле «+ добавить», повтор не задвоил; связь пропала на 3 скана — отметка ⏳ и «Не отправлено: 3» (и после перезагрузки), предупреждение при проведении, связь вернулась — итог ровно +3; двое начинают одну ревизию — один черновик, «весь склад» — «Присоединиться» (`web/e2e/revision-many-devices.spec.ts`). Режим поля по умолчанию, журнал строки, повтор с тем же `op_id`; сверка «= итог» по своим записям, op_id ввода, свежесть показа, единицы найденного товара очередь неотправленных сканов, перечитывание после проведения, прошлые нажатия без ответа (`web/src/lib/revisionCount.test.ts`, `revisionSync.test.ts`, `revisionQueue.test.ts`, `retrySame.test.ts`).
