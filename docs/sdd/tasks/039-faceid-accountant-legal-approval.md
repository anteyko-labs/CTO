# 039 — Рабочий день по лицу (Dahua), бухгалтер, подтверждение заправки юрлицом

Статус: сделано, выкачено 20.11.2026 (; ответы 1а — терминал Dahua на точке, 2 — проверка лицом на точке, 3а, 4 — все три режима настройкой, 5а)

## Зачем
Владелец 20.11.2026: «в боте у сотрудников кнопка „Начать рабочий день“, дальше лицо распознаёт терминал Face ID, так начинается день и считаются часы, так же заканчивается»; «пользователь „бухгалтер“ видит всё как владелец, кроме чистой прибыли»; «клиент на своей машине, платит юрлицо — в Телеграм и кабинет юрлица уведомление, он подтверждает заправку».

## Что меняется
### A. Рабочий день по лицу (ADR-200)
1. **Терминал.** В «Настройки → Терминал Face ID» владелец видит адрес приёма событий филиала `https://<сервер>/api/v1/faceid/dahua/<ключ>` (ключ — случайный, «Сменить ключ»), окно подтверждения (мин, по умолчанию 3). Этот адрес ставится в Dahua: «Сеть → Загрузка событий (HTTP)». В карточке сотрудника — «Номер в терминале» (UserID, под которым лицо заведено в Dahua; уникален в филиале).
2. **Бот.** У работника внизу кнопки «▶️ Начать рабочий день» / «⏹ Закончить рабочий день» (видна одна — по состоянию). Нажал — «Подойдите к терминалу и посмотрите в камеру (3 мин)», заявка ждёт. Терминал узнал этого сотрудника в окне — день начат (закончен), в бот: «Рабочий день начат в 09:02». Окно прошло — «Не подтверждено лицом, нажмите снова».
3. **Без кнопки.** Событие терминала без заявки ничего не начинает (день — только кнопка + лицо), пишется в журнал терминала. Неизвестный UserID, чужой ключ — 200 терминалу (чтобы не повторял), запись в журнал, без действия. Повтор того же события — без второго действия.
4. **Часы.** «Сотрудники → Табель»: месяц, строка на работника — по дням часы, итог часов; раскрыть день — начало/конец. Незакрытый день к концу суток (по Бишкеку) — «не закрыт», часы не считаются, владелец закрывает вручную временем (с причиной, журнал). Начисления не меняются (часы — только учёт).
5. **Права.** Табель и настройки терминала — владелец и право «Табель» (новое, не по умолчанию). Событие владельцу `staff.workday` (по умолчанию в ленту не идёт).

### B. Бухгалтер (ADR-201)
6. Роль `accountant`: заводит владелец в «Пользователи» (логин, пароль, имя). Видит всё, что видит владелец, во всех филиалах, **только просмотр** (3а): любой запрос, кроме чтения, — 403 (кроме входа, выхода, смены своего пароля). **Не видит чистую прибыль**: раздел «Прибыль и убытки», прибыль/маржа/себестоимость в отчётах, сводке, боте, помощнике — 403 или поля нет. Бота и помощника у бухгалтера нет.

### C. Подтверждение заправки юрлицом (ADR-202)
7. **Когда.** Касса проводит чек в долг юрлица (оплата «В долг» на фирму-клиента) — создаётся запрос «Подтвердите обслуживание»: машина, клиент, позиции, сумма, кассир. Уведомление — в Телеграм всем привязанным к фирме и в кабинет фирмы («Запросы» → «Подтвердить» / «Отклонить» с причиной); подтвердить может любой работник фирмы с доступом (5а). Решение — кассиру на экран и в ленту владельца `party.sale_approval`.
8. **Режим — настройка филиала** `legal.approval_mode` в «Настройки → Юрлица» (4: все три):
   - **а) ждать** — чек не проводится, пока фирма не подтвердит; касса показывает «Ждём подтверждения фирмы…», отклонили — чек не проведён, причина на экране;
   - **б) после** — чек проводится сразу в долг, подтверждение — отметка на чеке; отклонили — чек помечен «Фирма отклонила», владельцу событие, решает он (исправить/сторно — как сейчас);
   - **в) с таймаутом** (по умолчанию, N = 10 мин, `legal.approval_timeout_min`) — как «а», но не ответили за N минут — кассир может нажать «Провести без подтверждения» (отметка «без подтверждения» на чеке).
   - «Не спрашивать» (выкл.) — как сейчас.
9. Фирма без привязанного Телеграма и без входа в кабинет — запрос не создаётся, чек как сейчас, отметка «не спрошено».

## Данные, маршруты, права
- Миграции 0115 (A), 0116 (C), 0117 (B) — 0112–0114 заняты задачей 037.
- A: `faceid_devices(branch_id, key, window_min)`, `employees.faceid_user_id`, `faceid_events` (append-only, dedup), `workday_requests`, `work_sessions(employee_id, branch_id, started_at, ended_at, closed_by)`. `POST /faceid/dahua/{key}` (без входа), `GET|PUT /settings/faceid`, `GET /staff/timesheet?month`, `POST /staff/work-sessions/{id}/close`. Право `timesheet`.
- B: `users.role` + `accountant`. Проверка в извлечении пользователя: не GET — 403; список запретных путей прибыли — в одном месте.
- C: `sale_approvals` (sale/черновик, party, статус `pending|approved|rejected|expired|skipped`, решение, кто, причина). `POST /sales/approvals` (касса, режимы а/в — черновик чека), `GET /sales/approvals/{id}`, `POST /sales/approvals/{id}/force`; кабинет `GET /client/approvals`, `POST /client/approvals/{id}/approve|reject`; кнопки в боте `ap:ok:<id>` / `ap:no:<id>`.

## Не входит
Своя проверка лица сервером (лицо распознаёт терминал Dahua); геолокация; начисление по часам; подтверждение машин из задачи 037 (делается там).

## Проверка
- `server/tests/faceid.rs`: кнопка → событие Dahua в окне → сессия открыта, сообщение; вне окна — нет; чужой ключ/неизвестный UserID — 200 без действия; повтор события — одно действие; табель считает часы, незакрытый день — без часов, закрытие владельцем.
- `server/tests/accountant.rs`: GET отчётов 200, любой POST/PUT/DELETE 403, прибыль 403, себестоимости в ответах нет.
- `server/tests/sale_approval.rs`: режимы а/б/в/выкл; подтверждение из кабинета и из бота; отклонение; таймаут → «Провести без подтверждения»; фирма без контактов — «не спрошено».
- e2e — табель, вход бухгалтера (нет «Прибыли», нет кнопок записи), касса ждёт подтверждения.

## Решено без вопроса
- Лицо проверяет терминал Dahua, сервер принимает его событие (HTTP-загрузка событий) — новая библиотека не нужна.
- День начинается только кнопкой + лицом в окне: одно лицо без кнопки не считается, чтобы проход мимо терминала не открывал день.
- Режим по умолчанию — «в» с 10 минутами.
