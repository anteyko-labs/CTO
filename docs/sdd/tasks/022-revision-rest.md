# 022. Доп. ревизия на непосчитанное

Статус: черновик

## Зачем

Вопрос с точки 03.11.2026: «если не успели всю ревизию… основную закроем, доп. откроем чисто для того, что не успели». Сейчас новая ревизия показывает весь склад вместе с уже посчитанным: люди не видят, что осталось, а товар, который досчитали только на одной полке, получает ложную недостачу.

## Что меняется

- **Окно «Провести ревизию»** (владелец): галочка «Сразу открыть доп. ревизию — только то, что не посчитали» (по умолчанию выключена). После проведения открывается доп. ревизия, и экран сразу переходит в неё.
- **Проведённая ревизия**: кнопка «Досчитать непосчитанное» (владелец) делает то же самое, если галочку забыли.
- **Доп. ревизия** — обычный черновик (SPEC-15) того же охвата (весь склад или категория основной), в заголовке подпись «Доп. к ревизии № N — только то, что в ней не посчитали». В список не попадают товары, посчитанные в основной ревизии и во всей цепочке (доп. к доп. исключает посчитанное во всех предыдущих). Остальное как у любой ревизии: поиск, скан, «Товар не из программы», «Ещё считают», проведение владельцем, норма масла.
- **Товар, уже посчитанный в основной**: скан, «+ добавить», «= итог», «Сканер товаров» → 409 `counted_in_main` «„…“ уже посчитан в ревизии № N (X шт) — в доп. ревизию не входит» (вариант зависит от ответа на вопрос 1). «Найти в списке» показывает такие товары с пометкой «посчитан в № N», без кнопки «Посчитать».
- **Маршрут**: `POST /revisions {category_id?, comment?, rest_of?: uuid}`. `rest_of` принимается только у проведённой ревизии своего филиала (иначе 422). Охват берётся из неё, `category_id` в запросе не учитывается. Открытый черновик того же охвата уже есть — как сейчас: возвращается он (присоединиться), второй не заводится.
- **Данные**: миграция `0103_revision_rest_of.sql` — `revisions.rest_of uuid null references revisions(id)`. `GET /revisions` и `GET /revisions/{id}` отдают `rest_of_number`.
- **Права**: открыть доп. ревизию может только владелец, как любую новую (ADR-186). Администратор присоединяется к ней по прежним правилам.
- **Журнал**: `revision.create` с `rest_of` (номер основной).

## Не входит

- Автоматическая доп. ревизия без галочки или кнопки.
- Объединение отчётов основной и доп. ревизии в один (в «Ревизиях» они идут двумя строками, итоги каждой отдельно).
- Изменение проведённой основной ревизии (инвариант 4).

## Проверка

- `server/tests/revision_rest.rs` (новый):
  - основная «весь склад»: A посчитан, B и C нет → проведена; доп. ревизия показывает B и C, без A;
  - пересчёт A в доп. ревизии → 409 `counted_in_main`, остаток A не меняется;
  - проведение доп. ревизии меняет только B и C; сумма недостач двух ревизий равна недостаче одной полной ревизии;
  - доп. к доп. исключает посчитанное в обеих; охват категории наследуется;
  - `rest_of` у черновика или чужого филиала → 422; администратор → 403, а к открытой доп. ревизии присоединяется;
  - открытый черновик того же охвата → возвращается он; `/stock/verify` пуст.
- e2e `web/e2e/revision-rest.spec.ts`: галочка в окне проведения → открыта доп. ревизия без посчитанного; подпись «Доп. к ревизии № N»; скан посчитанного товара → сообщение; «Досчитать непосчитанное» с проведённой.

## Решено без вопроса

- Галочка по умолчанию выключена: обычная полная ревизия идёт как раньше.
- «Посчитано в основной» — это есть строка в её итогах (`revision_results`). Строка с 0 («не нашли») тоже считается посчитанной.
- Отдельный ADR не нужен: инварианты и контракты tier0/tier2 не нарушаются (начинает и проводит владелец, проведённое не меняется).

## Вопросы

1. В доп. ревизии сканируют товар, который уже посчитали в основной (например, нашли ещё коробку на складе). Что делать?
   а) Не пускать: «уже посчитан в ревизии № N (8 шт), найденное проведите оприходованием». Рекомендую: иначе посчитают только склад без витрины, и выйдет ложная недостача.
   б) Пускать как пересчёт заново: вписывать всё, что есть во всех местах, и остаток встанет по новому числу.
